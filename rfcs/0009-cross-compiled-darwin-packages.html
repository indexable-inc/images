Summary

Let a repo package opt into being cross-compiled from x86_64-linux to macOS with one metadata line, cross = true, and have the result transparently substitute onto Darwin clients from cache.ix.dev. The package registry collects every cross-tagged package; the per-system builder builds each one on the Linux CI host for aarch64-apple-darwin and x86_64-apple-darwin, publishes them as packages.x86_64-linux.<name>-<triple>, and aliases them into the native Darwin package namespaces (packages.aarch64-darwin.<name>, packages.x86_64-darwin.<name>). A macOS user running nix build .#<name> then downloads a prebuilt artifact instead of compiling. Package definitions stay target-agnostic: the cross lane swaps the Rust unit graph and the wrapper builder underneath a normal definition rather than asking it to branch on a target.

Motivation

The repo's primary target is x86_64-linux (the fleet, the CI runners, the image builds). But several repo-owned tools are things a developer wants locally on a Mac: nix-web-monitor (live web monitor for Nix builds), dag-runner, and more to come. Two facts collide:

  1. CI is Linux. The warm-store self-hosted runner pool that builds and caches every package is x86_64-linux. There is no Darwin builder in the CI path, so anything a Mac user needs must either be built on their own machine from source or produced on Linux.
  2. Building from source on a Mac is the bad outcome. A cold nix build of a Rust tool with a Svelte front-end on a laptop is slow, and it defeats the point of the fleet's binary cache. The whole value of cache.ix.dev is that ix up and nix build substitute artifacts rather than rebuild them; Darwin users were excluded from that benefit for any repo-native tool.

So the goal is: cross-compile the Mac-relevant tools on the Linux CI host, push their closures to the public cache, and make a Mac client's ordinary nix build .#tool resolve to that prebuilt closure. And do it declaratively — a package should say "I want a Mac build" in one line, not hand-roll a cross derivation.

The toolchain half of this already exists in the sibling ix repo (its nix/lib/apple-sdk-toolchain.nix); this RFC ports it and wires it to the package registry so opting in is a tag, not a bespoke build.

Detailed design

The metadata tag

A package opts in from its package.nix metadata:

# packages/dag-runner/package.nix
{ id = "dag-runner"; cross = true; /* ... */ }

packages/registry.nix adds cross to allowedMetadataKeys and normalizes it (normalizeCross). cross = true expands to the default descriptor; an attrset overrides individual knobs, with unknown keys rejected:

cross = {
  attrName = id;                       # flake attr stem; defaults to the package id
  exposeNativeDarwin = true;           # alias into packages.<darwin-system>.<name>
  systems = null;                      # build-host systems this applies to (null = all)
  targets = [ "aarch64-apple-darwin" "x86_64-apple-darwin" ];
};

The registry exposes crossEntriesFor system, the filtered list of tagged packages enabled for a given build-host system, mirroring the existing packageSetEntriesFor / flakeEntriesFor selectors. No backend, build, or wrap knobs: the tag declares intent, and the build lane owns mechanism.

The cross lane

All cross building happens in lib/per-system.nix and is gated on a Linux build host (lib.optionalAttrs pkgs.stdenv.hostPlatform.isLinux). For each Apple target, a cross-configured ix is constructed and handed to the package's ordinary default.nix:

crossIxFor = target:
  let targetWorkspace = crossWorkspace // {
        units = crossWorkspace.unitsFor { inherit target; };
      };
  in ix // {
    inherit pkgs;
    cargoUnit = ix.cargoUnitFor pkgs;
    rustWorkspace = targetWorkspace;                 # units now target the triple
    cross = { isCross = true; inherit target; targetSystem = targetSystemFor target; };
    # wrapPackage forced into cross mode so nativePathSuffix host tools drop out
    wrapPackage = wrapperPkgs: args: ix.wrapPackage wrapperPkgs (args // { isCross = true; });
  };

buildCrossPackage = target: entry:
  lib.callPackageWith (pkgs // { inherit entry repoPackages; ix = crossIxFor target; /* ... */ })
    entry.path { };

The critical property: the package's default.nix never mentions the target. packages/nix/nix-web-monitor/server/default.nix calls ix.rustWorkspace.units and ix.wrapPackage exactly as it does for a native build; the cross lane has swapped ix.rustWorkspace.units for the target unit graph and wrapped ix.wrapPackage to force isCross. A definition is written once and works native or cross.

Output naming and Darwin aliasing

Cross outputs are published under the Linux system, keyed by triple, and then aliased into the native Darwin namespaces:

crossPackages       # packages.x86_64-linux.<attrName>-aarch64-apple-darwin, ...-x86_64-apple-darwin
darwinPackageAliases # packages.aarch64-darwin.<attrName> -> the -aarch64-apple-darwin build
                     # packages.x86_64-darwin.<attrName>  -> the -x86_64-apple-darwin build

flake.nix merges the aliases into the Darwin package sets:

packages =
  rawPackages
  // lib.genAttrs [ "aarch64-darwin" "x86_64-darwin" ]
       (system: rawPackages.${system} // (linuxDarwinAliases.${system} or { }));

A Mac user's nix build .#nix-web-monitor resolves through the alias to a derivation built on Linux. Because the same store path is what CI pushed to cache.ix.dev, the build is a substitution, not a compile. exposeNativeDarwin = false opts a package out of aliasing while keeping the triple-suffixed output (for a package that should be fetched explicitly rather than shadow a native name).

The Linux→Darwin toolchain

Cross compilation of the Rust workspace (and its C/C++ dependencies) uses two pinned pieces, both overridable:

  • lib/darwin/macos-sdk.nix fetches a public repackaged MacOSX15.4.sdk tarball, pinned by SRI hash, unpacked into a store path. It is the sysroot for both the C compile and the Rust link. Override ix.macosSdk to supply your own SDK for a stricter licensing posture.
  • lib/darwin/apple-sdk-toolchain.nix builds the compiler/linker wrappers for a target triple: zig cc / zig c++ as the cross C/C++ compiler with the SDK as sysroot, and clang -fuse-ld=lld as the Rust linker. It returns { env, runtimeInputs, rustcArgsForPlatform }. env sets the per-target cargo variables (CARGO_TARGET_<T>_LINKER, CC_<t>, CFLAGS_<t>, SDKROOT, a CMake toolchain file, …) that nix-cargo-unit's renderer threads into each unit; rustcArgsForPlatform adds the framework search path only for the matching target so host and other-target units are untouched.

The wrapper scripts go through the repo's checked-bash writer (bash -n + shellcheck at build time). They rewrite argv to bridge spelling mismatches (Apple/clang arm64-apple-macosx vs zig's aarch64-macos), drop flags zig rejects (-arch, -m64), strip sanitizer flags the cross toolchain does not wire up, and pin ZIG_GLOBAL_CACHE_DIR to an action-local writable path so a sandboxed service user's read-only HOME does not cause a silent zig cc failure (ix ENG-1278).

Caching and publication

The cache-push workflow enumerates .#cachePushRoots.x86_64-linux, realises each derivation, and pushes the closures to the public ix-public atticd cache served at cache.ix.dev. The triple-suffixed cross outputs are part of that roots set, so their closures are pushed on every merge to main. The Darwin aliases point at those exact store paths, so a Mac client substitutes them. Publication is by derivation, not eval-time output path, because floating content-addressed outputs (the Rust workspace default) have no path until realised.

Migration

Adding a package to the Mac set is a one-line change: add cross = true to its package.nix. Nothing else in the package changes, because the definition was already target-agnostic (or becomes so by using ix.rustWorkspace and ix.wrapPackage rather than reaching for pkgs directly). Removing a package is deleting the line. The initial set is dag-runner and nix-web-monitor.

Drawbacks

  • The lane is Linux-only, and that has sharp edges on a Mac. The Apple (zig + SDK) and Rust target graph run on a Linux build host; a Darwin host cannot host this lane. Worse, evaluating a triple-suffixed output on a Mac forces the Rust unit-graph IFD, which is an x86_64-linux derivation and fails with a platform mismatch during evaluation. So the alias only works as a substitution: if the cache has the path, the Mac user gets it; if the cache is cold (or the closure was never pushed), the Mac user cannot build it locally and gets an evaluation/build failure rather than a slow-but-working fallback. Cache availability is load-bearing, not an optimization.
  • No Haskell. GHC Linux→Darwin cross is a category problem for this setup; nix-output-monitor (Haskell) is deliberately excluded and must be handled by a native Darwin build path later, not this lane.
  • Trust and provenance of Apple binaries. The artifacts are Mach-O binaries built on Linux with a repackaged SDK and served from our cache; they are not signed or notarized. Gatekeeper friction and the supply-chain question ("who built this Mac binary") are real and unaddressed here.
  • SDK licensing. Apple licenses the macOS SDK for use on Apple hardware. The default fetches a public repackaged tarball; that posture is inherited from the sibling ix repo but is a legal consideration each consumer should weigh, hence the ix.macosSdk override.
  • Untested-on-target. With no Darwin CI, nothing actually runs the produced binary on macOS in the pipeline. Cross builds can link clean and still fail at runtime (a dlopen, a framework version, an arch mismatch). Confidence comes from developers running them, not from a gate.
  • x86_64-darwin is built but barely used. Producing both Apple triples doubles the cross build cost, and the Intel-Mac output gets little real exercise.

Alternatives

  • Do nothing; Mac users build from source. Simple and always correct, but slow and cache-defeating for exactly the tools people want locally. Rejected as the default experience.
  • Native Darwin CI builders. Add macOS runners to the pool and build natively. This is the most robust answer (real toolchain, real ABI, can smoke-test on target) and would also unlock Haskell. It is rejected for now on cost and operational surface (managing Mac runners), and it is the obvious future direction, not a competitor to this lane.
  • Stock nixpkgs pkgsCross.<darwin>. Use nixpkgs' own cross machinery. In practice it drags in the same SDK-licensing question, needs per-package cross plumbing, and does not compose with the repo's nix-cargo-unit per-unit graph as cleanly as threading the toolchain env through the existing renderer. The zig-based toolchain is already proven in the sibling repo.
  • osxcross or a hand-built cctools/ld64 cross toolchain. The traditional route. More moving parts and more brittle than zig cc + lld, which give a single, well-maintained cross C/C++ compiler and linker with SDK-sysroot support out of the box.
  • Per-package bespoke cross derivations. Let each package write its own cross build. This is what the design explicitly avoids: it scatters target logic across definitions and makes the common case verbose. The registry tag + cross-configured ix keeps definitions target-agnostic.

Prior art

  • The sibling ix repo's nix/lib/apple-sdk-toolchain.nix. The direct source of this toolchain; the same 15.4 SDK tarball and hash are reused, so the SDK store path is shared between repos.
  • zig cc as a cross compiler. Zig ships a full clang + libc/sysroot cross toolchain reachable through one binary; using it as the cross C/C++ compiler with -isysroot is an established pattern well beyond this repo.
  • nixpkgs pkgsCross and the cross-compilation infrastructure. The general model of a build platform producing host-platform artifacts, and the CARGO_TARGET_<T>_* conventions this lane sets.
  • RFC 0005 (cargo-drv). The Rust workspace unit-graph builder whose unitsFor { target = ...; } hook this lane calls to produce a per-target unit graph. The cross lane is a consumer of that renderer's per-platform hooks.
  • The package registry's existing target selectors. packageSet, flake, and overlay normalization in packages/registry.nix established the "tag in package.nix, collect in the registry, realize in per-system.nix" shape that cross follows.

Unresolved questions

  1. How do we guarantee a cache hit before a Mac user pulls? Because local build on Darwin is impossible (IFD platform mismatch), a merged-but-not-yet-pushed package is broken for Mac clients until cache-push completes. Should the Darwin alias be gated on a cache-presence check, or is "merge then wait for the push job" acceptable?
  2. Which packages belong in the Mac set? The tag makes opting in trivial, which makes over-tagging easy. What is the criterion — "a developer runs this locally on a Mac" — and who curates it?
  3. Do we keep building x86_64-darwin? Given the Apple-silicon-dominated fleet, is the Intel-Mac triple worth its build cost, or should it be opt-in per package rather than a default target?
  4. How do we get any on-target signal? Without Darwin CI, is there a lightweight smoke test (even a manual, periodic "does it launch" check) worth formalizing, or do we accept build-only confidence until native runners exist?
  5. Signing / notarization. Do the produced binaries need codesigning to be pleasant to run under Gatekeeper, and if so where in the pipeline does that live?
  6. The Haskell gap. nix-output-monitor is excluded. Is the answer a native Darwin build (needs runners), a static musl-style trick that does not apply to Mach-O, or leaving it Linux-only indefinitely?

Future possibilities

  • Native Darwin CI runners. The clean long-term answer: build (and test) natively on macOS, keep this cross lane as a fast path or retire it, and finally cover Haskell.
  • Cross to aarch64-linux. The same registry-tag + cross-configured-ix shape generalizes to non-Darwin targets; the tag could grow a target set beyond the two Apple triples.
  • Codesigning and notarization. A post-build signing step (with a credential delivered the way the cache-push token is) would make the artifacts first-class on locked-down Macs.
  • On-target verification job. If even a single Mac runner appears, a cheap "substitute the pushed closure and launch it" check would convert build-only confidence into runtime confidence without a full native build pipeline.
  • Shared cross artifacts across repos. Since the SDK store path is already shared with ix, identical cross toolchain inputs could let the two repos substitute each other's cross dependency closures.
